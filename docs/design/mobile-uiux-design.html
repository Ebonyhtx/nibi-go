3 · WORK 形态 = 同源 UI 直接承载（不自绘）

源码实证（nibi-client）：packages/web/src/main.tsx:18 从 @nibi/ui 挂载 Root——桌面的同一套外壳/任务列表/会话；main.tsx:480 注释原文「Web 远程控制模式虽然复用了 web UI，但它背后其实挂着 desktop」。配对后的 workspace「归既有 bootstrap」（web-remote-control/CONTRACT.md）。PWA 截图里的登录卡 / 选择电脑 / 桌面主体 / 任务会话，就是这套 UI 本体——WORK 直接承载，不再有第二份实现。

@nibi/ui · Root + 工作区外壳 桌面同一套组件与「纸上鸟」主题真源——桌面上什么样，WORK 里就什么样
packages/web/src/web-remote-control/ui/* 手机专属 admission 面：登录卡、DeviceListPage（选择电脑）、ScanPage、连接中/失败页、切换账号
@nibi/client · connectViaProtocol / relay transport 连接与帧协议同源（默认路径；注入路径见下）
NIBI-GO · WebView 载体（原生壳） WORK = WebView 加载同源 web 构建；原生只做壳与系统衔接
两个上游接缝
① createWebPlatform({ externalWebRemoteControlProxy })（main.tsx:458，现成）：原生壳按 IPlatformService 注入通知 / 保活 / secure store / 更新；
② 票据 T7 · transport 注入口（待上游实现）：宿主注入已实现的 transport——contracts/transport.ts 的对外行为面（状态枚举 / onPayload / onStateChange / reloadPage）已齐备，WebSocketCtor 注入参数是先例。

4 · E2E：案 A 原生隧道（已拍板，D9 修订）

为什么：WebView 里跑 web 自建连接 = 与 PWA 同为明文，且 WebView 切后台 JS 暂停、连接断——后台通知/保活全失效。手机远控的主场景是「人不在电脑前」，通知是核心体验；Phase A 已建成的原生链路不该废弃。

层职责实现来源
原生（App 进程）relay 连接、心跳、replay、E2E keyneg、token、通知、前台服务GO 仓 packages/relay-client（已建成已测）+ nibi-keepalive / notifications
bridge（postMessage）状态迁移 + 已解密帧流双向转发；WebView 刷新/崩溃时原生连接保持GO 仓新增载体桥
WebView（web UI）同源 UI 只消费状态与帧、走原发送通道上游 T7 注入口
影响面结论
桌面零改动零影响
浏览器 PWA代码纯增量（不传注入 = 逐字同路径），行为不变、维持明文
服务端 / relay零改动（D9 承诺继续成立）
NIBI-GO App五张原生远控屏退役 → WebView 载体；GO 主体 / 登录 / 通知 / 保活保留
桥上实现期决策（届时确认）：WebView 内登录 = 复用原生已登录 token（推荐，免二次登录） vs WebView 独立走一遍 PWA 登录。
