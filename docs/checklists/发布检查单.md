# 发布检查单（A4 收尾）

> 状态：分发方式与签名方案**已定**（2026-11-11）；发布链路已落地。
> 原则：凭据（keystore 口令、发布 token）**不进对话、不进仓库、不落盘到仓库目录**（AGENTS 规则 14）。
> 密钥材料、备份与恢复步骤由运营者在本仓之外的私有运维位置保管；本文件只记录公开可验证的信息。

## 0. 已定方案

### 0.1 分发方式：A · 源码仓 GitHub Releases ✅

- 产物发在 `Ebonyhtx/nibi-go` 的 Releases（仓库公开，匿名 `releases/latest` 可读）
- 更新检查器默认指向该仓（`app/src/relay/updater.ts` 的 `RELEASE_REPO`），可用 `EXPO_PUBLIC_NIBI_RELEASE_REPO` 在构建时覆盖
- 校验闭环：GitHub 为每个上传资产算 `digest`（`sha256:...`），客户端 **fail-closed**——缺摘要即拒装
- 迁移预案：若将来源码仓转私有，改用独立发布仓 `nibi-go-releases`，只需构建时改环境变量并重新出包；旧版用户需过渡期双发

> 备选方案（未采用，保留记录）：独立发布仓（解耦源码/产物）、R2 + 自定义 manifest（灰度/强制更新）、纯手动分发。

### 0.2 签名密钥库：本机工作副本 + 私有运维保管 ✅

| 项目 | 公开信息 |
|---|---|
| 工作副本 | 只在签名时临时存在；`keystore.mjs wipe --yes` 可删 |
| 备份与恢复 | 由运营者在私有运维位置保管，步骤不写入本仓 |
| 证书指纹（公开） | `39:D4:5F:4E:…:6A:48`（完整值见 `SECURITY.md`），用于验包与自查 |

- 密钥库类型 **PKCS12**（JDK 9+ 默认；storepass 与 keypass 同一口令）
- 证书：RSA 4096，有效期 10000 天（≈27 年），`CN=NIBI-GO, O=NIBI Studio, C=CN`
- **不可逆**：Android 覆盖升级强制同签名。一旦发布首个公开版，换钥 = 所有用户卸载重装（配对凭据一并丢失）
- 构建注入：`app/plugins/withReleaseSigning.js`（config plugin，prebuild 自动落盘）——
  release 构建缺密钥库或 `NIBI_KEYSTORE_PASS` 时**直接失败**，不回落 debug

### 0.3 运维侧保管

密钥材料、口令与恢复步骤统一由运营者在本仓之外的私有运维位置保管，不在本仓展开。

### 0.4 杀软白名单材料（发布后）

- 产物 SHA-256 + 版本说明 + 应用包名（`top.nibistudio.nibigo`）+ 开发者信息
- 误报截图（真机清单 I3 记录）→ 提交各厂商误报申诉（dsh-Go 经验：预留 1-2 周）

## 1. 发布流程（每次，一条命令）

```bash
# 口令来源：环境变量 NIBI_KEYSTORE_PASS（由运营者私有保管，不写入仓库）
node scripts/release.mjs 0.1.1 --notes "本次变更摘要"
```

脚本按顺序执行（任一步失败都会把 `app.json` 回滚）：

| 步骤 | 动作 |
|---|---|
| 1 | 版本号 `expo.version` + `expo.android.versionCode` 同时前进（Android 只认 versionCode） |
| 2 | `check-boundaries` / `check-public-repo` / 全量测试 / typecheck |
| 3 | 检查密钥库工作副本（缺失则提示 `keystore.mjs restore`，不自动从远端拉） |
| 4 | `expo prebuild --platform android`（把版本号与签名配置落到 `android/`） |
| 5 | `gradlew assembleRelease --no-daemon`（`--no-daemon`：daemon 会缓存环境变量） |
| 6 | `apksigner verify --print-certs` 与密钥库指纹比对 |
| 7 | `gh release create` 上传 APK |
| 8 | 回查 GitHub 资产 `digest`，缺失或不一致即报错（客户端会拒装） |

签名密钥库的公开校验操作：

```bash
node scripts/keystore.mjs fingerprint      # 打印证书指纹（公开信息）
node scripts/keystore.mjs verify <apk>     # 校验某个 APK 的签名证书
```

备份、恢复与轮换步骤由运营者在私有运维位置维护，不在本仓记录。

## 2. 发布前检查清单

| # | 项 | 依据 |
|---|---|---|
| P1 | 版本号与 versionCode 均已前进 | 脚本第 1 步 |
| P2 | 全量测试/门禁/typecheck 绿 | 脚本第 2 步 |
| P3 | 真机验证清单（`docs/checklists/真机验证清单.md`）关键项通过或如实标注 | 规则 12 |
| P4 | release APK 用发布证书签名（`apksigner verify --print-certs` 与 `SECURITY.md` 指纹一致） | 脚本第 6 步 |
| P5 | SHA-256 与 Release 资产 `digest` 一致 | 脚本第 8 步 |
| P6 | 更新覆盖安装实测（旧版 → 新版，同签名） | 真机项 H2 |
| P7 | PWA/旧桌面兼容回归（E3/E5） | D9 降级 |
| P8 | 杀软材料准备（误报记录 + 申诉） | §0.4 |

## 3. 发布后

- 观察更新检查器命中（旧版用户升级率）
- 异常回滚 = **发布更高版本号**（不删旧版；删了老客户端会查不到）
- 每次发布把版本/commit/SHA-256 记到 Release notes

---

## 4. 灾难恢复（换机器 / 重装）

恢复步骤与密钥材料由运营者在私有运维位置保管，不在本仓记录。恢复完成后必须用
`node scripts/keystore.mjs fingerprint` 核对证书指纹与 `SECURITY.md` 一致。

> 密钥库丢失 = 无法再发可覆盖升级的版本。恢复演练由运营者按私有运维流程定期执行。
