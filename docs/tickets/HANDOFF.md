# 上游协作方式（票据制）

> 背景：本仓（NIBI-GO）与 nibi-client 是两个独立仓库。本仓依赖的上游能力缺口以**票据**形式
> 记录在 [`docs/tickets/`](.)，由维护者转交上游；**上游按自身节奏处理，本仓不催排期**
> （D17 单向消费纪律）。

## 票据清单

| 票据 | 归属 | 内容 |
|---|---|---|
| T1 | nibi-client 内核 | android 平台包发布 |
| T2 | nibi-client 内核 | npm scope 统一 |
| T3 | **已结案** | NIBI-GO OIDC native app 已注册（client `399176882886606853`）并接入令牌代理；剩真机走完整登录 |
| T4 | **已结案（GO 侧修复）** | 审批卡恒空；归因修正：桌面无缺口，客户端缺 V4 握手与 optionId（见 T4 末节） |
| T5 | nibi-client 桌面 transport | **已实现**（`9d0fc7c0`，2026-11-12）；待真机 |

## 处理方式（三步）

1. **票据落仓**：每张票据按"给上游维护者看的任务书"标准写——现状证据（文件:行号）、
   具体改动清单、验收标准、边界承诺（不影响上游）。
2. **上游复核**：上游自行核对票据现状描述是否属实，并按自己的流程决定实现/拒绝/改造；
   票据不设 deadline，不改变上游优先级。
3. **本仓被动消费**：实现随上游发版后，本仓升级 lockfile 版本 + 在
   [ADR-INDEX](../decisions/ADR-INDEX.md) 登记新 commit，按 [plan.md](../plan.md) §4 冒烟。

## 边界承诺

| 顾虑 | 现实 |
|---|---|
| 票据会不会打断上游正在做的事 | 不会——票据只在被明确指到时才被阅读，平时不进入上游流程 |
| 会不会带偏上游方向 | 不会——票据均为**纯增量**且写明边界承诺；上游有权拒绝或改造 |
| 会不会被要求"为 NIBI-GO 而设计" | 不会——验收只描述本仓的消费诉求（能编译/能拉到包），实现按上游自己的规范 |
